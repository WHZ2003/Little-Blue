# 两台电脑轮流使用：完整交接

此流程用于同一只大肥鱼在两台**可信、配合操作的电脑**之间轮流运行。
旧端停止收发并保存后才出包，新端校验后恢复到新卷，最后接管。
不需要云服务，不会自动重新扫码，不合并两端各自新增的分叉历史。

## 两台设备都要先安装本功能

已准备好的 `backups/DaFeiYu-handoff-update-2026-10-21.zip` 可以复制到另一台。
解压到临时目录，按其中 README.txt 执行 Install.ps1；安装器校验文件、备份旧源码，
且要求目标核心已经停止，不会覆盖密钥、数据库或 Compose 配置。

两台设备使用同一份包含 `handoff.ps1` 和 `little_blue/handoff*.py` 的源码。
在各自项目目录运行 `setup.ps1` 安装依赖并构建/启动新核心。
已经安装依赖时可用 `start-core.ps1` 构建升级。首次交接前，两台都应已有
可健康启动的 Docker 核心、独立 `.secrets`，以及自己的 `.env`（API key 不随交接传送）。
接收端首次启动未绑定微信也可以，不要为了准备交接先扫码。

机器身份保存在本机 `.handoff/device-private.pem`，不要把 `.handoff` 目录从一台电脑
复制到另一台；两个设备必须各自生成密钥。该目录和包都不会进入 Git。
保持接收端私钥不丢失，否则无法解密已经指定给它的交接包。

以下所有命令在对应电脑的大肥鱼目录执行。文件路径按实际复制位置调整。

## A → B

### 1. B 生成接收请求

```powershell
.\handoff.ps1 Prepare -Request .\backups\B-request.json
```

B 会暂停新任务、等待当前消息处理完、关闭自身的桌宠远程客户端和核心，
并锁住原数据卷。把 `B-request.json` 复制到 A。请求只有公钥和随机编号，
不含登录凭据或记忆；状态命令显示的设备编号可用于确认接收设备。

### 2. A 停止收发、保存并交出

```powershell
.\handoff.ps1 Send -Request .\backups\B-request.json -Package .\backups\A-to-B.lbhand
```

执行顺序：

1. 持久写入“正在交接”，拒绝桌面新任务及设置写入，停止主动活动。
2. 当前 iLink 长轮询返回后不再发起下一次轮询；本轮已收到的消息先落库并处理。
3. 等待当前模型任务、已接收消息队列及在途图片发送结束，最长 5 分钟。
4. 关闭本项目的远程桌宠客户端，关闭核心的 Docker 自动重启，正常停止核心，
   确认进程已经退出且退出码为 0。
5. 对最终数据库做快照。记录已读游标、去重表、对话及送达状态、提醒和预算，
   保留成长/事实版本、虚拟手机等数据。
6. 用 B 的公钥加密记忆和已有微信凭据，持久标记 A 已交出，然后发布交接包。

把 `A-to-B.lbhand` 复制到 B。**A 从此保持停止，不能直接重新启动使用旧记忆。**
`start.ps1`、`start-core.ps1`、`setup.ps1`、微信管理脚本会检查主机锁；
绕过这些脚本直接启动新版核心，数据卷里的锁仍会阻止它运行。

### 3. B 恢复并接管

```powershell
.\handoff.ps1 Receive -Package .\backups\A-to-B.lbhand -Receipt .\backups\B-receipt.json
.\start.ps1
```

B 验证指定设备、接收请求、加密认证、归档校验、数据库完整性及代次，恢复到
新的命名卷。原卷保留，不覆盖。生成的 `compose.override.yaml` 让今后的常规
启动命令继续使用新卷。不要删除这个文件以“恢复旧端”。

新端不发起扫码登录，而是复用交接包中已有的机器人凭据、消息游标和去重记录。
同一时刻只有新端继续轮询；不重发已确认或结果不明的旧消息。
模型、联网设置、提醒和预算继承原端；电脑工具与环境感知默认关闭，须在新设备
按需重新开启。API key 必须在新设备自己的 `.env` 配置。

若源端没有微信绑定，新端仍未绑定；若旧凭据已在服务端失效，新端会显示过期，
不会自动重新扫码。只有确认旧端仍锁定后，才在新端显式扫码恢复。
同一 token 跨设备是否被服务端接受，需用你的账号实际验证，程序不宣称腾讯保证此行为。

### 4. A 确认交接完成

将 `B-receipt.json` 复制回 A：

```powershell
.\handoff.ps1 Finish -Receipt .\backups\B-receipt.json
```

A 校验 B 的签名和对应包的摘要，记为“已完成交出”。回执不会解锁 A。
回执确认的是 B 核心已健康启动、恢复已完成，不代表微信服务器已接受凭据或对方已读。

## B → A

完全反向执行：A `Prepare` 生成**新请求**；B `Send` 导出最新历史；
A `Receive`；B `Finish`。必须传递当前活跃端刚导出的包，不能重新导入上次的旧包。
返回包代次递增，持续保留同一条记忆历史。

## 状态和失败重试

```powershell
.\handoff.ps1 Status
```

| 状态 | 含义及下一步 |
| --- | --- |
| `active` | 本机可运行；可作为下一次交出端 |
| `awaiting` | 本机已经停止，等待本次请求的交接包；重复 Prepare 会重发同一个请求 |
| `sending` | 交出过程被中断；使用同一个 Request 和 Package 路径重试 Send |
| `released` | 包已发出，旧端锁定；转移包，等待接收回执 |
| `receiving` | 恢复/启动被中断；使用同一个包重试 Receive |
| `retired` | 对方确认接管；下一次轮到本机时执行 Prepare 接收回传 |

重复接收已经成功的**当前包**只返回已有回执，不重置记忆。交回后再导入旧包会被拒绝。
中断导入留下的部分卷不会启用；重试会使用新卷，部分卷留作诊断。
导出失败或超时后也不会自动恢复旧端收发，避免包实际上已经传出时出现双活。

当前版本没有“强制夺回”或无条件解锁按钮。如果对方尚未接管，也优先完成本次
交接后按反向流程交回。若包、私钥或磁盘损坏，保留两边原卷和 `.handoff` 状态，
停止操作后检查；不要通过删除锁文件或手动启用旧卷来猜测恢复。
若 5 分钟内仍有审批/任务未结束，先在原桌面处理或取消该任务，再重试 Send。

## 保证范围

保存并迁移**旧端已经收到并落库**的聊天、记忆与送达状态。停机窗口内仍滞留在
腾讯服务器的消息，是否保留/补发由 iLink 决定，无法承诺零丢失；交接期间请短暂停聊，
新端启动后发送 `/status` 再继续。手机微信会话界面的历史仍由微信管理。

这是配合式离线交接，不是有中心租约服务器的分布式锁。它防止本流程中的误启动、
错设备导入和旧包重放；无法阻止管理员故意复制密钥/卷、删除锁或运行不带保护的旧镜像。
因此两台必须都升级，且不要并行运行手动复制出来的旧实例。

加密采用 RSA-OAEP-SHA256 包装随机 AES-256-GCM 密钥，回执用接收端 RSA-PSS 签名。
包指定到接收设备；只有它的本机私钥可以解密。API key 不在包中。包仍应只交给你
信任的另一台电脑。接收请求须来自你准备好的目标设备；这不是第三方身份认证系统。
交接载荷上限 256 MiB，目前支持 Docker + iLink、标准 `/data` 命名数据卷；
Windows UI 桥接激活时拒绝交接。
